CALENDLY — WHY IT CANNOT HANDLE CANDIDATE SLOT BOOKING (EPIC 5.2 / 5.4)
===================================================================================
Date: March 2, 2026
Author: DeskZero Engineering
===================================================================================

SCOPE OF THIS DOCUMENT
-----------------------
We are NOT asking Calendly to handle the full scheduling pipeline.
Our backend handles everything:
  ✅ Epic 1  — Interview settings at JD creation
  ✅ Epic 2  — Stage transition triggering the workflow
  ✅ Epic 3  — Dashboard status column
  ✅ Epic 4  — Candidate sidebar Interview tab + logs
  ✅ Epic 5.1 — Panel availability collection (DONE — our panel form)
  ✅ Epic 6  — Interview day automation + reminders + voice calls
  ✅ Epic 7  — Post-interview notes, transcript, AI assessment, feedback
  ✅ Epic 8  — Round progression loop

The ONLY question this document answers:

  "Can Calendly handle Epic 5.2 + 5.4 — showing available slots
   to the candidate and confirming the booking — while our backend
   saves the result and handles everything else?"

ANSWER: No. Here is exactly why.


-------------------------------------------------------------------
SECTION 1: WHAT EPIC 5.2 / 5.4 REQUIRES
-------------------------------------------------------------------

From the product spec (interview_scheduler.pdf):

  Story 5.2 — Candidate Invitation:
    Agent emails candidate a scheduling request to choose from
    available slots. (Slots come from panelist_availability table.)

  Story 5.4 — Confirm Slot + Block Calendars:
    Candidate selects slot.
    Agent confirms matching panel availability.
    Calendar invites sent to panel member(s) and candidate.
    Status: "Scheduled — calendar blocked."

What our system provides as INPUT to the booking step:
  - panelist_availability table: each panelist's confirmed free slots
    stored as JSONB (collected via our panel form — Part 1 COMPLETE)
  - interview_id, application_id, round_config_id — all in our DB
  - candidate email — in our candidates table

What the booking step must OUTPUT back to our DB:
  - interview.status = SCHEDULED
  - interview.scheduled_start, scheduled_end
  - interview.panelist_email (which panelist was assigned)
  - interview_timeline_events log entry


-------------------------------------------------------------------
SECTION 2: THE ROOT BLOCKER — CALENDLY CANNOT READ OUR DB SLOTS
-------------------------------------------------------------------

This is the single reason everything else fails.

After Part 1 completes, our DB has:

  panelist_availability table:
    panelist_email: "alice@company.com"
    interview_id:   XYZ
    available_slots: [
      { date: "2026-03-10", slots: [{ start: "14:00", end: "15:00" }] },
      { date: "2026-03-11", slots: [{ start: "10:00", end: "11:00" }] }
    ]

  Alice explicitly confirmed THESE slots for THIS specific interview.

How Calendly Round Robin determines what to show to the candidate:
  It does NOT read from any external database.
  It reads ONLY from each panelist's connected Google/Outlook calendar.
  It checks their real-time free/busy.

  There is NO Calendly API to say:
    "Show the candidate these specific slots from our DB."

  To bridge this gap we need a sync layer:
    Alice submits our form → parse her JSONB →
    call Calendly API to push slots into her Calendly account.

  This means:
    - Every panelist needs a Calendly account (new friction)
    - Part 1 data must be duplicated into Calendly after every
      submission (new engineering, new failure point)
    - If sync drifts → candidate sees wrong slots or no slots

  Example drift:
    Alice submits at 11:58 PM. Our DB updates instantly.
    Calendly sync queued. Candidate hits booking page at 11:59 PM.
    Calendly shows Alice as UNAVAILABLE. Valid slot lost.
    At midnight sync runs. Too late — candidate gave up.


-------------------------------------------------------------------
SECTION 3: REMAINING BLOCKERS EVEN IF SYNC IS BUILT
-------------------------------------------------------------------

BLOCKER 1: BOOKING LINK IS NOT SCOPED TO AN APPLICATION
--------------------------------------------------------

From Story 5.2: "Email candidate a scheduling request."

This email must contain a link scoped to THIS candidate's
specific application — not a generic portal link.

  Application #1001 — Rahul → Round 1 Technical Screen
  Application #1002 — Priya → Round 1 Technical Screen

  What we send:
    Rahul: /booking?token=<JWT: interview_id=ABC, app_id=1001, exp>
    Priya: /booking?token=<JWT: interview_id=DEF, app_id=1002, exp>

    JWT signed with our SECRET_KEY.
    Tamper it → 401. Forward it → already SCHEDULED → 409.

  What Calendly provides:
    One Round Robin link for the entire event type:
      https://calendly.com/yourcompany/technical-round
    Same URL for Rahul and Priya.

    utm_source workaround:
      https://calendly.com/yourcompany/technical-round?utm_source=app_1001
    This is plain text — not signed, not verified.
    Rahul can change app_1001 to app_1002. Calendly passes it through.
    Anyone can book on any application's behalf.

  This is a security failure, not a cosmetic issue.
  The booking link IS the only security boundary for a
  no-login candidate-facing page.


BLOCKER 2: OVERLAPPING PANELIST SLOTS COLLAPSE — CAPACITY LOST
---------------------------------------------------------------

After Part 1: two panelists submitted for the same interview.

  Alice → free March 10, 2–3 PM
  Bob   → free March 10, 2–3 PM

  This means two candidates can be scheduled for 2–3 PM.
  One books with Alice. Another books with Bob.

  What Calendly Round Robin shows:
    [ March 10 — 2:00 PM – 3:00 PM ]  ← ONE slot only

  Bob's 2–3 PM is invisible. His hour goes unused.
  Capacity = 1 instead of 2.

  At scale: 5 panelists free 2–3 PM = 5 slots in our system,
  1 slot in Calendly. Four hours wasted silently.


BLOCKER 3: PANELIST ASSIGNMENT ARRIVES VIA WEBHOOK — NOT ATOMIC
----------------------------------------------------------------

From Story 5.4: once slot confirmed, we must:
  update interview.panelist_email, interview.status = SCHEDULED,
  log to interview_timeline_events, send confirmation emails.

  With Calendly:
    T+0ms    Candidate books on Calendly page
    T+~500ms invitee.created webhook fires to our server
    T+~501ms We update our DB

  Gap T+0 to T+501ms: interview is confirmed in Calendly
  but NOT yet in our DB. If webhook fails:

    Scenario A — Webhook fails (503 during our deployment):
      Calendly retries after 5 minutes.
      For 5 minutes: Calendly confirmed. Our DB: "Candidate invited."
      HR sees wrong status. Cannot advance candidate. Email not sent.

    Scenario B — Webhook fires twice (Calendly retry):
      Without idempotency logic: double DB update, double
      confirmation email to panelist. Extra engineering required.

  In our custom system:
    POST /api/candidate/book-slot is ONE DB transaction.
    slot booked + interview updated + event logged = atomic.
    No webhook. No delivery gap. No retry complexity.


-------------------------------------------------------------------
SECTION 4: WHAT CALENDLY ACTUALLY REPLACES VS WHAT YOU STILL BUILD
-------------------------------------------------------------------

  What Calendly handles for Epic 5.2/5.4:
    ✅ Renders a date picker UI to the candidate
    ✅ Sends a basic Calendly-branded confirmation email

  What your backend must STILL build regardless:
    ❌ Availability sync layer (panelist_availability → Calendly)
    ❌ Calendly account per panelist (onboarding friction)
    ❌ Webhook receiver + idempotency + retry handling
    ❌ Secure application-scoped booking link (utm_source is not enough)
    ❌ Branded confirmation emails with round/job/candidate details
    ❌ interview_timeline_events logging
    ❌ Concurrent booking protection (two candidates, same slot)
    ❌ Cancellation/rescheduling re-trigger flow

  What you save by using Calendly:
    Building a frontend date picker component.
    Approximately 1–2 days of frontend work.

  What Calendly costs:
    ~$16/seat/month per panelist (Teams plan required)
    Engineering time: sync layer + webhook infra + idempotency
    Security gap: booking links not application-scoped
    Data gap: slot capacity halved on overlapping availability


-------------------------------------------------------------------
SECTION 5: FINAL ANSWER
-------------------------------------------------------------------

Even scoped to ONLY Epic 5.2/5.4 (candidate slot booking),
Calendly cannot be plugged in without:

  1. A full sync layer pushing Part 1 DB data into Calendly
     — duplicating a completed, working system
  2. Accepting insecure booking links (no signed application_id)
  3. Accepting slot capacity loss on overlapping panelists
  4. Building webhook infrastructure with idempotency handling

All four require engineering work that is more complex than
building the booking endpoint + a frontend date picker directly.

The work to BUILD CUSTOM:
  Backend: ~2 days (booking service, slot repo, JWT helper)
  Frontend: ~1–2 days (date picker component)

Part 1 is done. The booking page is the only remaining piece.
Build it custom. Own the data. Keep the security. No sync needed.
