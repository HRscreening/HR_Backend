SECTION 2: WHAT WE ARE BUILDING
-------------------------------------------------------------------

A fully custom candidate slot booking system that:

  1. Computes individual bookable slots from panelist availability
  2. Stores each slot as a separate DB row (one per panelist)
  3. Generates a secure, expiring, application-scoped booking link
  4. Sends the link to the candidate via email
  5. Lets the candidate view available slots and pick one
  6. Atomically books the slot (prevents double booking)
  7. Assigns the panelist, updates interview status
  8. Sends confirmation emails to both candidate and panelist
  9. Logs every event in interview_timeline_events

SECTION 3: DATA FLOW (END TO END)
-------------------------------------------------------------------

  [HR moves application to a round]
          ↓
  move_to_round() creates an Interview row
  + sends panelist availability request emails
          ↓
  [All panelists submit availability via panel form]
  → stored in panelist_availability table
          ↓
  [Background job: compute_interview_slots]
  → reads all panelist_availability rows for the interview
  → expands each slot window into flat rows
  → inserts into interview_slots table
  → sets interview.status = READY_TO_BOOK
  → generates booking_token JWT (encodes interview_id,
    application_id, expires in N days)
  → sets interview.booking_token + booking_token_expires_at
  → sends booking link email to candidate
          ↓
  [Candidate clicks link in email]
  → GET /api/candidate/booking-form?token=<JWT>
  → backend decodes token, validates expiry + status
  → returns list of available slots grouped by date
          ↓
  [Candidate selects a slot]
  → POST /api/candidate/book-slot?token=<JWT>
    body: { slot_id: "uuid" }
  → backend decodes token
  → SELECT ... FOR UPDATE SKIP LOCKED on interview_slots row
  → if already booked → 409 Conflict
  → if free → mark slot booked, update interview:
      status = SCHEDULED
      scheduled_start = slot.slot_start
      scheduled_end   = slot.slot_end
      panelist_email  = slot.panelist_email
  → log SLOT_BOOKED event in interview_timeline_events
  → send confirmation email to candidate
  → send confirmation email to panelist
          ↓
  [Interview is now SCHEDULED ✅]

SECTION 4: NEW DATABASE TABLE — interview_slots
-------------------------------------------------------------------

  Table: interview_slots

  Column                    Type          Notes
  ------------------------- ------------- --------------------------
  id                        UUID (PK)     auto-generated
  interview_id              UUID (FK)     → interviews.id
  panelist_availability_id  UUID (FK)     → panelist_availability.id
  panelist_email            VARCHAR       denormalized for speed
  panelist_name             VARCHAR       denormalized for emails
  slot_start                TIMESTAMPTZ   start of the bookable slot
  slot_end                  TIMESTAMPTZ   end of the bookable slot
  is_booked                 BOOLEAN       default False
  booked_at                 TIMESTAMPTZ   nullable, set on booking
  created_at                TIMESTAMPTZ   auto

  Indexes:
    - (interview_id, is_booked) — for fast slot lookup
    - (interview_id, slot_start) — for date-grouped display

  Key design decision:
    Each panelist × each slot window = ONE row.
    If Panelist A and Panelist B are both free 2–3 PM,
    that is TWO rows in this table, not one.
    This directly enables "two candidates can book 2–3 PM"
    because each row is independently lockable.

  Example rows for one interview:

  id    | panelist_email     | slot_start          | slot_end            | is_booked
  ------|--------------------|--------------------|---------------------|----------
  row1  | alice@company.com  | 2026-03-10 14:00   | 2026-03-10 15:00   | false
  row2  | bob@company.com    | 2026-03-10 14:00   | 2026-03-10 15:00   | false
  row3  | alice@company.com  | 2026-03-10 15:00   | 2026-03-10 16:00   | false

  → Two candidates can book 2–3 PM (row1 and row2 are separate)
  → One candidate books 3–4 PM with Alice (row3)

SECTION 7: CONCURRENCY CONTROL STRATEGY
-------------------------------------------------------------------

  The critical section is book_slot().

  Implementation:
  ---------------
  async def book_slot(slot_id, interview_id, db):
      # Step 1: Lock the row — no other transaction can
      #         touch this row until we commit or rollback
      slot = await db.execute(
          SELECT interview_slots
          WHERE id = slot_id
          AND interview_id = interview_id
          FOR UPDATE SKIP LOCKED   ← key clause
      )

      # Step 2: If SKIP LOCKED returned nothing, another
      #         transaction holds the lock → already being booked
      if not slot:
          raise DomainError(409, "Slot is currently being booked")

      # Step 3: Check if already confirmed booked
      if slot.is_booked:
          raise DomainError(409, "Slot already taken")

      # Step 4: Mark as booked atomically within this transaction
      slot.is_booked = True
      slot.booked_at = datetime.utcnow()
      await db.commit()

  Why SKIP LOCKED instead of plain FOR UPDATE:
    FOR UPDATE would make the second request WAIT for the lock.
    SKIP LOCKED makes the second request immediately return nothing.
    → Better UX: candidate B gets instant "slot taken" feedback
      instead of hanging.

SECTION 8: BOOKING TOKEN DESIGN
-------------------------------------------------------------------

  Token type: JWT (signed with our SECRET_KEY)

  Payload:
  {
    "interview_id":   "uuid",
    "application_id": "uuid",
    "type":           "candidate_booking",
    "exp":            <unix timestamp, e.g. +7 days>
  }

  Properties:
    ✅ Expiring — candidate cannot book after expiry
    ✅ Signed   — cannot be tampered to change interview_id
    ✅ Typed    — "candidate_booking" type prevents reuse
                  of other JWT types (auth tokens etc.)
    ✅ One per round — each Interview row has its own token
    ✅ Invalidated after booking — once interview.status =
       SCHEDULED, backend rejects further booking attempts
       with 409 "Interview already scheduled"

  Token is embedded in the email link:
    https://deskzero.app/schedule?token=<JWT>

  The frontend passes the token as a query param to our API.
  No session, no login required for the candidate.
