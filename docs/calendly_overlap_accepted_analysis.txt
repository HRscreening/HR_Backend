===================================================================================
CALENDLY — WHAT HAPPENS IF WE ACCEPT OVERLAPPING SLOT CAPACITY LOSS?
===================================================================================
Date: March 1, 2026
Author: DeskZero Engineering
Premise: We accept that two panelists available at 2–3 PM = only ONE bookable
         slot shown to candidates (not two). Capacity loss is tolerated.
===================================================================================


-------------------------------------------------------------------
SECTION 1: THE CONCESSION WE ARE MAKING
-------------------------------------------------------------------

Normal behaviour we designed:
  Panelist A: free 2–3 PM
  Panelist B: free 2–3 PM

  Candidate sees:
    [ 2:00 PM – 3:00 PM ]  ← bookable by Candidate 1
    [ 2:00 PM – 3:00 PM ]  ← bookable by Candidate 2
  Total capacity = 2

What we are now accepting (Calendly Round Robin):
  Candidate sees:
    [ 2:00 PM – 3:00 PM ]  ← bookable by Candidate 1 only
  Total capacity = 1

  Panelist B's 2–3 PM slot is invisible and goes unused.

This is a real business cost — we are accepting it as a known
trade-off for this analysis. Even with this concession, let us
examine whether Calendly is now viable.


-------------------------------------------------------------------
SECTION 2: WHAT IS STILL BLOCKED — PROBLEM BY PROBLEM
-------------------------------------------------------------------

REMAINING PROBLEM 1: AVAILABILITY SYNC — PART 1 IS ALREADY BUILT
-----------------------------------------------------------------

Our current state:
  Part 1 is COMPLETE.
  Panelists receive an email with a link.
  They open OUR form and submit their available time slots.
  Data lands in our `panelist_availability` table as JSONB:

    panelist_availability row:
    {
      panelist_email: "alice@company.com",
      available_slots: [
        { date: "2026-03-10", slots: [{ start: "14:00", end: "15:00" }] },
        { date: "2026-03-11", slots: [{ start: "10:00", end: "11:00" }] }
      ]
    }

What Calendly Round Robin needs:
  Alice must have a Calendly ACCOUNT.
  Her Calendly calendar availability must show March 10, 2–3 PM as free.
  Round Robin reads availability from Calendly's internal calendar,
  NOT from our database.

  So to plug Calendly in, even now, we must:

  Step A: After alice@company.com submits our panel form,
          call Calendly API to create/find her Calendly user.

  Step B: Call PATCH /user_availability_schedules to inject
          her slots into her Calendly account.

          API call example:
          PATCH https://api.calendly.com/user_availability_schedules/{uuid}
          {
            "timezone": "Asia/Kolkata",
            "rules": [
              {
                "type": "wday",
                "wday": "tuesday",
                "intervals": [{ "from": "14:00", "to": "15:00" }]
              }
            ]
          }

          But this API sets RECURRING weekly availability, NOT
          one-off date-specific slots. One-off date overrides
          require a separate "schedule override" endpoint.

  Step C: For each specific date Alice submitted, we must call
          POST /schedule_overrides to override her default schedule
          for that exact date.

  Step D: When Alice's token is submitted and availability is saved
          in our DB, we now also must sync to Calendly.
          If that sync fails → Calendly shows her as unavailable
          even though our DB has her availability.

  Step E: If Alice resubmits or changes her availability,
          we must DELETE old overrides and re-POST new ones.

  RESULT:
  We are now maintaining two parallel availability systems.
  Our DB is the source of truth. Calendly is a manually synced
  mirror of it. Every panelist submission now triggers:

    save to panelist_availability table  ← already works
    + sync to Calendly API               ← new engineering work

  This sync layer is not trivial. It requires:
    - Calendly user lookup or creation per panelist
    - Date-specific override management per slot
    - Error handling and retry if Calendly API is down
    - Cleanup of stale overrides if panelist resubmits

  Example failure scenario:
    Alice submits availability at 11:58 PM.
    Our DB saves instantly. ✅
    Calendly sync job is queued but delayed.
    At 11:59 PM a candidate hits the booking page.
    Calendly shows March 10 2–3 PM as UNAVAILABLE (not yet synced).
    Candidate cannot book Alice's slot.
    At midnight the sync job runs and Calendly updates.
    But the candidate already gave up and closed the page.
    → Valid slot was invisible. Booking opportunity lost.


REMAINING PROBLEM 2: BOOKING LINK HAS NO APPLICATION IDENTITY
-------------------------------------------------------------

Calendly Round Robin generates one event link for the whole team:

  https://calendly.com/deskzero-portal/technical-round

This link is the SAME for ALL candidates applying to Technical Round.

Example:
  Application #1001 — Rahul Sharma      → moves to Round 1
  Application #1002 — Priya Mehta       → moves to Round 1
  Application #1003 — Amit Verma        → moves to Round 1

  All three receive:
    https://calendly.com/deskzero-portal/technical-round

  There is NO way to distinguish who booked via which application.
  When a booking comes in, Calendly fires a webhook:

    {
      "event": "invitee.created",
      "payload": {
        "invitee": {
          "email": "rahul@gmail.com",
          "name": "Rahul Sharma"
        },
        "event": { "start_time": "2026-03-10T14:00:00Z" }
      }
    }

  Notice: NO application_id, NO interview_id, NO round_config_id.

  We only know "someone named Rahul Sharma with email rahul@gmail.com
  booked a slot." We must then query our DB:

    SELECT * FROM applications
    JOIN candidates ON candidates.id = applications.candidate_id
    WHERE candidates.email = 'rahul@gmail.com'
    AND applications.current_round = 1
    AND applications.status = 'IN_REVIEW'

  Problems with this lookup:
    - Candidate may have MULTIPLE open applications
    - Candidate email may not match exactly (typo in Calendly form)
    - If two candidates share an email (rare but possible), lookup
      returns multiple rows and we cannot resolve which one booked
    - If webhook fires twice (Calendly retries), we process it twice

  Calendly DOES allow "utm_" query params on the link:
    https://calendly.com/deskzero-portal/technical-round?utm_source=1001

  These params are passed through to the webhook payload as
  `tracking.utm_source`. So we COULD embed application_id there:
    https://calendly.com/deskzero-portal/technical-round?utm_source=app_1001

  BUT:
    - utm_source is a plain visible query param, not a signed token
    - Anyone who sees the URL can change utm_source=app_1001 to
      utm_source=app_9999 and book on behalf of another application
    - There is no signature or expiry — it is not a security mechanism
    - It is a tracking convention, not an auth mechanism

  To make this safe we would need to sign and verify it ourselves —
  which is exactly what our booking_token JWT does, just without
  Calendly in the middle.

  Example attack:
    Rahul Sharma receives his booking link:
      https://calendly.com/deskzero-portal/technical-round?utm_source=app_1001
    He changes utm_source to app_1002 (Priya's application).
    He books a slot. Webhook fires with utm_source=app_1002.
    Our system marks Priya's interview as SCHEDULED with Rahul's
    booking details. Priya never booked. Her interview is poisoned.


REMAINING PROBLEM 3: PANELIST ASSIGNMENT ARRIVES AFTER BOOKING
--------------------------------------------------------------

When a candidate books via Round Robin, Calendly internally picks a
panelist. We only find out who was assigned via a webhook.

Timeline:
  T+0ms   Candidate submits booking on Calendly page
  T+0ms   Calendly confirms booking to candidate
  T+800ms Calendly fires invitee.created webhook to our server
  T+801ms Our server updates interviews.panelist_email

The gap between T+0 and T+801 is small normally, but:

  Scenario A — Webhook delivery failure:
    Our webhook endpoint is behind a load balancer that is doing
    a rolling restart. Calendly gets a 502. It retries after 5 min.
    For 5 minutes, our DB has a SCHEDULED interview with
    panelist_email = NULL. Any HR dashboard query for scheduled
    interviews returns malformed data.

  Scenario B — Webhook processed out of order:
    Candidate books. Webhook 1 fires.
    Candidate cancels on Calendly immediately after.
    Webhook 2 (invitee.cancelled) fires.
    Network delay causes Webhook 2 to arrive BEFORE Webhook 1.
    We process "cancelled" first, then "created".
    Interview ends up marked SCHEDULED even though it was cancelled.
    This is a real race condition with external webhook systems.

  Scenario C — No panelist in our DB:
    After booking, we want to send a confirmation email to the
    assigned panelist (from our own email service).
    But panelist_email is empty until the webhook fires.
    If we send the confirmation email from the webhook handler:
      - It works when webhook is reliable
      - It silently fails if webhook is delayed or dropped
    We have no atomic guarantee like we do with our own DB transaction.

  In our custom system:
    book_slot() is one DB transaction.
    At commit time: slot.is_booked = True, interview.panelist_email = set,
    interview.status = SCHEDULED, timeline event logged.
    Everything in one atomic operation. No webhook. No race condition.

  With Calendly:
    Booking confirmation → DB update are two separate systems
    connected by a fire-and-forget HTTP call (webhook).

SECTION 3: WHAT CALENDLY ACTUALLY SAVES US
-------------------------------------------------------------------

If we accepted all remaining problems above and built the sync layer,
Calendly would replace exactly ONE thing:

  The candidate-facing booking page UI.

  Without Calendly: we build a simple frontend page with a
    date picker that calls GET /api/candidate/booking-form
    and POST /api/candidate/book-slot.

  With Calendly: Calendly renders that date picker for us.

That is the entire value exchange. We would be:

  Building:
    - Availablity sync layer (Calendly API integration)
    - Webhook receiver with retry handling
    - Application ID embedding + validation workaround
    - Orphaned interview cleanup job (for missed webhooks)
    - Calendly account management per panelist

  Saving:
    - Building a frontend date picker component

  The frontend date picker is 1–2 days of frontend work.
  The Calendly integration is 1–2 weeks of backend work
  plus ongoing maintenance and a monthly per-seat bill.

  The math does not work.

SECTION 5: CONCLUSION
-------------------------------------------------------------------

Even with the generous concession of accepting slot capacity loss,
Calendly Round Robin remains impractical for DeskZero because:

  1. Our availability data lives in our DB. Syncing it to Calendly
     creates a fragile, duplicate system with drift risk.

  2. Calendly has no concept of application_id. Booking attribution
     requires either insecure URL params or complex email-based
     reverse lookup — both error-prone.

  3. Panelist assignment via webhook is not atomic. It creates a
     window where our DB is in an inconsistent state.

The overlap concession removes one aesthetic concern (duplicate
time slots on the UI). It does not touch the data ownership,
link security, or atomicity problems — which are the real blockers.

FINAL ANSWER: Calendly is not viable even if overlap is accepted.
Build custom. The scope is small: a booking service + a frontend
date picker. Everything else is already in place.
